# SAGE Security Model

## Security posture

SAGE is a local-first Electron desktop companion. The renderer is treated as untrusted UI code and privileged work remains in the main process. Online access, voice input, desktop context, and consequential tools are explicit capabilities rather than defaults.

## Trust boundaries

1. **Renderer → preload:** the renderer receives only the allowlisted APIs exposed by `contextBridge`; Node integration is disabled and context isolation/sandboxing are enabled.
2. **Preload → main IPC:** every IPC handler must authenticate the sender against the current `BrowserWindow` webContents. Inputs crossing IPC must be type- and size-validated.
3. **Main → operating system:** filesystem, shell, notifications, window control, and process operations are privileged. External URL opening is restricted to HTTP(S).
4. **Assistant → tools:** tool execution is mediated by `ToolPolicy`. Write, external, and destructive operations require confirmation; network-dependent operations require network permission.
5. **Plugins → core:** plugins use a versioned manifest and remain behind the policy boundary. The current registry is in-process; third-party plugin code is therefore trusted application code, not a security sandbox.
6. **Persistence → runtime:** memory, reminders, and experience data are schema-validated and recovery paths must quarantine malformed state rather than execute or trust it.

## Threats and controls

| Threat | Primary control |
|---|---|
| Renderer attempts privileged IPC | Sender authentication + explicit preload allowlist |
| IPC payload abuse | Bounded strings and numeric range checks |
| Stale/replayed confirmations | Expiring, single-use bounded confirmation vault |
| Renderer crash loop | Bounded recovery budget with process shutdown fallback |
| Unwanted network access | Global network permission + policy checks |
| Unauthorized microphone permission | Local renderer + network + voice preference gate |
| Malicious external navigation | Navigation allowlist + popup denial |
| Unsafe external URL | HTTP(S)-only shell opening |
| Plugin privilege escalation | Manifest validation + policy boundary; no renderer/Electron access |
| Corrupt persisted state | Schema validation, normalization, quarantine/recovery |
| Dependency install scripts | CI installs with lifecycle scripts disabled |

## Release requirements

Before a production release:

- `npm run validate:package` passes.
- `npm run check` passes.
- Dependency audit passes at the configured severity gate.
- Windows packaging succeeds from a clean checkout.
- The installer artifact is inspected before publication.
- Manual smoke testing covers launch, wake, conversation, safe actions, denied/confirmed actions, movement, restart, and persistence.
- Release signing is configured before distributing an installer as an official SAGE build.

## Dependency and lockfile policy

SAGE currently has no committed npm lockfile. Until a reproducible lockfile is committed, release automation must not claim byte-for-byte dependency reproducibility. A future lockfile change should be generated by npm from the declared dependency set and then CI/release should use `npm ci` with lifecycle scripts disabled where compatible with the packaging workflow. A hand-written lockfile must never be substituted.

## Plugin isolation policy

The current in-process plugin registry is appropriate only for built-in/trusted integrations. Third-party plugin support must not be enabled under this model. Before accepting untrusted plugins, move execution into a separately permissioned process/sandbox with a narrow message protocol and explicit capability enforcement.

## Reporting

Do not disclose suspected vulnerabilities publicly before a fix is available. For a private project, report security issues to the repository owner through a private GitHub security channel when available.
